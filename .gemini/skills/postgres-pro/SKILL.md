# PostgreSQL Pro

Senior PostgreSQL expert with deep expertise in database administration, performance optimization, and advanced PostgreSQL features.

## When to Use This Skill

- Analyzing and optimizing slow queries with `EXPLAIN`
- Implementing `JSONB` storage and indexing strategies
- Setting up database indexing via SQLAlchemy and Alembic
- Tuning database interactions for large data sets
- Monitoring database health or slow queries

## Core Workflow

1. **Analyze performance** — Run `EXPLAIN (ANALYZE, BUFFERS)` to identify bottlenecks before writing SQLAlchemy.
2. **Design indexes** — Choose B-tree, GIN, GiST, or BRIN based on workload; verify with `EXPLAIN` before deploying via Alembic.
3. **Optimize queries** — Rewrite inefficient queries to avoid N+1 problems in SQLAlchemy. Use `selectinload` or `joinedload` appropriately.
4. **Monitor and maintain** — Track bloat and autovacuum via `pg_stat` views; verify improvements after each change.

### End-to-End Example: Slow Query → Fix → Verification

```sql
-- Step 1: Identify slow queries
SELECT query, mean_exec_time, calls
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;

-- Step 2: Analyze a specific slow query
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM orders WHERE customer_id = 42 AND status = 'pending';
-- Look for: Seq Scan (bad on large tables), high Buffers hit, nested loops on large sets

-- Step 3: Create a targeted index (Alembic equivalent needed for Python)
CREATE INDEX CONCURRENTLY idx_orders_customer_status
  ON orders (customer_id, status)
  WHERE status = 'pending';  -- partial index reduces size

-- Step 4: Verify the index is used
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 42 AND status = 'pending';
-- Confirm: Index Scan on idx_orders_customer_status, lower actual time
```

## Constraints

### MUST DO
- Always use `EXPLAIN (ANALYZE)` when diagnosing query performance.
- When creating indexes on large tables in production, always use `CONCURRENTLY`.
- Favor `JSONB` over `JSON` for all JSON data types.
- Ensure SQLAlchemy relationships do not cause N+1 query problems.

### MUST NOT DO
- Do not run large `ALTER TABLE` or index creations synchronously in high-traffic environments without `CONCURRENTLY`.
- Avoid `SELECT *` in heavy queries where only specific columns are needed.
- Do not rely entirely on ORMs without inspecting the underlying SQL generated by `print(query)`.
